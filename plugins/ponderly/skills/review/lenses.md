# Lenses

The review skill reads this file and launches one `review-arm` per `##` section below, all at once, and sends each arm the shared standard, the sentences of this paragraph from "Across every lens" to its end, together with that arm's own `##` section as the lens, so the standard reaches every arm once and no section repeats it. A section added here is an arm added, a section removed is an arm removed, and a section reworded changes what that arm looks for; the skill's steps stay as they are. Each lens names the categories its findings carry, from the arm block's list. Across every lens, a finding worth reporting is one a competent senior reviewer would expect the author to address before merge: true and verifiable against the code at head, a real concern that would improve the change, and specific enough to act on. A finding not worth reporting is an incorrect or unverifiable claim, a duplicate, a style nit below the project's bar, or advice that would not improve the change or would make it worse. A pre-existing problem in a touched file counts when it is verifiable. A finding sits where a change is needed. When a defect needs its own edit at several places, because each is wrong on its own, such as a stub and the interface it lacks or one mistake copied into several places, write one finding at each place you verified at head, in whatever file it is, touched or not, and one at each copy in the same file. When an edit at either of two places alone would fix the defect, such as a new call into a handler whose guard does not serve that call, or code and a document, configuration or manifest that now disagree, write one finding at the place the pull request changed, or one at each when it changed both, and when it changed neither side's lines, as when it only removed code, on the lines next to the removal. Each such finding names the file and line of the others, or of the other place when there is one finding, and never describes another place's defect as a sentence in place of a finding of its own; a place you suspect but have not verified at head is no finding and goes under unsure. A message describes one defect and no aside restating a claim you did not verify: a second defect, even on the same lines, is a finding of its own.

## correctness

This lens looks for code that does the wrong thing: logic errors, wrong conditions and comparisons, off-by-one bounds, wrong computations, values used before they are set or after they change, state read now that is written later or elsewhere, such as a debounced or deferred save, a snapshot taken before an async step completes, or a callback that lands after the next action, so that the action in between sees stale state, mishandled `None`, empty and boundary inputs, and behaviour that contradicts what the title, the body, a docstring or the surrounding code says it should do. It carries the category `correctness`, where most of a review's real findings sit. A true positive names the input or state that produces the wrong result, traces it through the code at head and says what the code does instead. The commonest wrong finding overlooks an existing guard or rests on a premise the code does not bear out, so the arm checks for a guard, a caller's precondition or a type that already rules the case out before reporting. A false positive asserts a bug the code already prevents, guesses at a caller's behaviour without reading it, or proposes a simplification that changes the behaviour or data shape downstream code reads. Error handling, concurrency, resource use and speed belong to the reliability lens; a swallowed exception that makes a function return a wrong result sits on the boundary, and this lens reports it only when the wrong result is the point. A comment or docstring that is stale while the code is right belongs to the documentation lens.

## reliability

This lens looks for code that fails badly or slowly: errors that are swallowed, masked or reported as success, missing handling for a call that can fail, retries and timeouts that are missing or unbounded, races and shared state under concurrency, including an operation started again before the previous one finishes, a second click, event or request, whose deferred work then lands on the wrong state, resources that are not released, faults that cascade instead of degrading, configuration defaults that can silently pick the wrong environment or provider, and dependency, build and CI changes that break or weaken the pipeline. It also looks at performance: unnecessary work in a loop, N+1 queries, inefficient algorithms on inputs that grow, unbounded memory and leaks. It carries the categories `reliability` and `performance`. A true positive names the failure or the load that triggers it, the path through the code and what the user or operator sees, such as a reported success for an operation that did not happen; a performance finding names the input size or call pattern that makes the cost real. A false positive asks for error handling where the caller already handles it, flags a theoretical race on state that is never shared, or calls code slow without an input that makes it so. A wrong result on the happy path belongs to the correctness lens, an exploitable failure to the security lens, and a configuration file's comment or description that no longer matches what it runs to the documentation lens.

## security

This lens looks for concrete, exploitable vulnerabilities, covering at least injection (SQL, shell, template and similar, where untrusted input reaches an interpreter by concatenation or formatting), authentication and authorisation (a missing check, a check on the wrong subject, a bypass path, broken access control), secrets in code (a credential, key or token written into the source, configuration or tests, with its actual value), unsafe deserialisation of input the user controls, and path traversal (a path built from input that can escape its intended directory); it also covers cryptographic misuse, data exposure and supply-chain risks. It carries the category `security`, the smallest share of a review and the highest bar, because a security finding that cannot be exploited here costs the reviewer more trust than any other kind. A true positive traces a specific data flow from the untrusted source to the dangerous sink in this code, or shows the bypass path, the secret's value or the deserialised input, and says what an attacker gains. A false positive restates a best practice without showing how it is exploited here, such as boilerplate sanitisation advice, a generic warning to pin an action to a SHA or a mutable-tag alert, even when it names the variable or the action; it also includes a flow whose input is not in fact user-controlled or is already validated. A bug with no attacker in it belongs to the correctness or reliability lens.

## maintainability

This lens looks for what makes the change harder to read, change or use than it needs to be: names and structure that contradict the conventions of the surrounding code, duplicated domain logic that will drift, needless complexity, dead code, and misleading or redundant patterns; a public contract that is missing its docstring, and a comment or docstring that describes the algorithm instead of the intent; API contracts, function signatures, type design and module boundaries that are awkward, leaky or inconsistent with the rest of the codebase; and user interfaces that shut out users, through missing accessibility or hard-coded text that defeats internationalisation. It carries the categories `maintainability`, `api-architecture` and `accessibility`, the readability and usability side of a review. A true positive points at the specific code and the local convention or the interface it is inconsistent with, and says what the reader or caller gets wrong because of it; a small finding is still a true positive when it names a concrete inconsistency or a typo in a public name, and is then low severity. A false positive is a personal preference with no local convention behind it, a comment that could be pasted onto any codebase unchanged, or a refactor that would not make this change better. Anything that changes behaviour belongs to the correctness, reliability or security lens, and stale, misleading or contradicting text to the documentation lens.

## documentation

This lens looks at the text a reader acts on: every Markdown file, template, help text, changelog, documentation page, workflow or configuration file the change touches, read in full at head, and the documentation elsewhere that the change makes untrue. In those files it looks for text that contradicts the code or the commands it describes, broken markup such as unmatched tags, bad links and malformed front matter, examples that would not run as written, and typos, wrong terms and unprofessional wording in user-facing text, interface labels and help strings included. For documentation the change makes stale, list each symbol, option, command, path or file the change renames, removes or alters, search the repository for each name, and judge only the text, comments and docstrings included, that names one of them; a comment or docstring that no longer matches code that is right is this lens's, and code that does not do what its docstring says is the correctness lens's. Do that search even when the change touches none of those files, and do not read every documentation file in the repository. It carries the category `documentation`. A true positive quotes the sentence and says what it contradicts at head or what a reader does wrong because of it; an example that would not run as written, text that tells a reader to do the wrong thing, markup that hides content, and a broken link in a quickstart or install path are medium, any other broken link and a typo or wrong term are low, and only text whose instructions lose data or break a user's setup is high. A false positive is a style preference or a rewording with no reader cost. A change to a workflow or configuration file that breaks or weakens the build or CI, such as a step that runs a script the change renamed, belongs to the reliability lens; this lens takes such a file's comments, names and descriptions only where they contradict the commands or code they name.

## testing

This lens looks at the tests the change adds or should have added: behaviour the change introduces or alters with no test that would fail if it broke, missing boundary and error cases for new code paths, tests that assert the wrong thing or nothing, tests that restate an implementation constant or check their own input, fakes that do not enforce the real contract, flaky tests that depend on time, order or the network, and validation logic in the tests themselves. It carries the category `testing`. A true positive names the code path or case that is untested or wrongly tested and the test that would cover it, in the project's own test framework and style. A false positive asks for coverage of code that an existing test already covers, demands tests for trivial code the project does not test, or proposes a test that would not catch a real regression. A defect in the production code itself belongs to the lens that covers that kind of defect; this lens reports that the tests miss it.
